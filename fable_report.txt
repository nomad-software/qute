Review of qute, 2026-11-10 (third pass)

The four bugs from the last report are fixed. This pass found one new crash, one visible-window bug, one large API gap and several smaller issues. Nothing in the repo was changed except this file.

Baseline, all clean on the current tree: go vet, gofmt, go test ./... (normal and qute_debug), and regeneration in a scratch copy produces no diff. Probes ran in a scratch module outside the repo; "confirmed" below means I ran it, "read" means I only read the code.

1. Crash: a layout item used after its layout is gone (confirmed)

    w := qtwidgets.NewQWidget(nil)
    lay := qtwidgets.NewQVBoxLayout(w)
    lay.AddWidget(qtwidgets.NewQLabelWithText("hi", nil))
    it := lay.ItemAt(0)
    w.Delete()
    it.IsEmpty()        // SIGSEGV in QLayoutItem::isEmpty

- it.Alive() is still true after the delete, so there is no panic, only the segfault.
- QLayoutItem and QSpacerItem are plain classes: Qt creates and frees them and qute never hears of it. ItemAt, TakeAt on a borrowed wrapper, and QLayoutItem.SpacerItem() all hand these out.
- CLAUDE.md says of this limitation "None are bound today", and COVERAGE.md reports 0 "results whose death qute cannot see". Both are wrong: the report only counts Parented results, and these are Borrowed.
- depends-on would fit: an item from ItemAt depends on the layout it came from. That needs the dependency to come from the receiver of the call, since QLayoutItem has no getter for its layout.

Final pass: this is one case of a wider hole. Any wrapper of a class that is neither a QObject nor a notify-dtor class is never told its object died, and a QObject reached through a second base class gets such a wrapper too, because the registry is keyed by the QObject address. More confirmed cases:

- QPaintDevice: d := painter.Device(), then delete the painter and the image; d.Alive() is true and d.Width() segfaults. The same applies to a widget or pixmap seen as a paint device.
- QGraphicsTextItem (a QObject) seen through scene.Items(): the result is a second, Borrowed handle. After txt.Delete() the text handle is Dead but the item handle says Alive, and it.Pos() reads freed memory and returns (0,0) with no panic. QGraphicsWidget and QGraphicsProxyWidget have the same shape.
- A QSpacerItem built in Go and given to a layout stays "Parented, Alive" after the layout is destroyed.
- By the same reading (not run): a nested QLayout seen as a QLayoutItem, and a QWindow seen as a QSurface.

A fix for the second-base case is to register the secondary address as an alias of the same handle when the object is first wrapped, so both pointers find one handle. The plain-class cases need depends-on from the receiver, as above.

2. GC deletes a visible QWindow (confirmed)

    w := qtgui.NewQWindow(nil)
    w.Show()            // drop w, GC: the window is deleted while on screen

- The visibility filter in qtwidgets/application_manual.cpp only pins objects where isWidgetType() is true. QWindow, QRasterWindow and a QOpenGLWindow without Go overrides are not widgets, so they are never pinned.
- This breaks the stated rule "GC must never delete something the user is looking at".

3. Most default arguments cannot be passed at all (confirmed)

Trailing default arguments are dropped and there is usually no second form that takes them. 925 bound methods have dropped defaults; only 6 overlay entries (keep-defaults, full) restore any. Things an app cannot do today:

- Tree models: Index(row, column), RowCount(), ColumnCount() and HasChildren() take no parent, so a caller cannot reach below the top level.
- Roles: Data(index) and SetData(index, value) take no role; QStandardItem.SetData(value) likewise.
- Text selection: QTextCursor.MovePosition(op) has no KeepAnchor mode and no count.
- Layouts: AddWidget(w) has no stretch or alignment, AddStretch() has no factor, QGridLayout.AddWidget has no alignment.
- QWidget.SetWindowFlag(flag) cannot clear a flag (the "on" argument is gone).
- QComboBox.AddItem(text) has no user data; QMessageBoxInformation and friends have no button choice; NewQFontWithFamily has no size.

This is the biggest practical problem in the project. It is not a safety issue, but the README's "broad coverage" claim hides it, and COVERAGE.md has no section for it. A generated "full" twin for every method with defaults would close it in one generator change.

4. Windows and dialogs with ordinary handlers are never freed (confirmed)

    d := qtwidgets.NewQDialog(nil)
    b := qtwidgets.NewQPushButtonWithText("ok", d)
    b.OnClicked(func(bool) { d.Accept() })
    d.Show(); d.Hide()  // drop d

- 50 such dialogs: 0 freed after GC. Without the reference to d in the closure: 50 of 50 freed.
- The closure lives in a cgo.Handle, which is a GC root, and it refers to d. Go cannot collect a cycle that passes through C.
- Nearly every real window has a handler that refers to the window, so "automatic cleanup by default" does not hold for them. The README only warns about a parentless object's own connections.
- Go subclasses with no parent are the same (50 made, 0 freed). That one is documented, but qute vet skips every New...With constructor, so it never flags it.
- I see no clean fix. It should at least be documented, and the scaffold and README could show Delete() or DeleteLater() on close (WA_DeleteOnClose is the usual Qt answer).

5. Memory of value classes is invisible to the Go GC (confirmed)

- 100 QImages of 16 MB each, created one per event and dropped without Delete(): RSS went from 47 MB to 1575 MB. The GC never ran, because the Go heap only grew by a few kilobytes.
- Inside one handler it is worse in principle: nothing can be freed until the handler returns, because only the event loop drains the cleanup queue.
- An app that loads images or pixmaps in a loop will grow without bound unless it calls Delete(). The README presents GC as sufficient for value classes.
- A common fix is to count the bytes of large value objects (QImage, QPixmap, QByteArray-backed things) and call runtime.GC() when the total since the last collection passes a threshold.

6. Objects returned from a Go override stay Owned by Go (read)

- goVirtRet in cmd/qutegen/types.go passes the pointer back to Qt and applies no ownership rule.
- The case that matters is a Go model's MimeData override. QAbstractItemView::startDrag gives the result to QDrag, which deletes it later but does not reparent it. The Go handle is still Owned and unreachable, and the drag runs a nested event loop, so the cleanup queue can free the QMimeData mid-drag. QDrag then holds a dangling pointer and deletes it again.
- I did not run this; driving a real drag offscreen was more than this pass justified.
- The other object-returning overrides (CreatePopupMenu, FocusObject) look harmless. A return rule on virtuals (transfer-to-cpp for mimeData) would close it.

7. t.Fatal inside qute.Run kills the test binary (confirmed)

- CLAUDE.md says it hangs. It now aborts instead: "panic: runtime error: panic called with nil argument" from rt.PostSync, and no later test runs.
- The cause is that Goexit runs PostSync's deferred recover, which returns nil, and the caller re-panics with that nil.
- The scaffold from "qute new" does this in screenshot_test.go (t.Fatalf and t.Fatal inside Run). The repo's own tests do too: model_test.go:41, qute_test.go:52, 69, 148, 155, opengl_test.go:39.
- These only bite when a test fails, which is when a clear message matters. A vet rule for it would be cheap.

8. qute vet owned-leak: false positive and blind spots (confirmed)

- False positive: b := NewQPushButtonWithText("ok", d) followed by b.OnClicked(...) is reported as "Owned ... never parented". The check in cmd/qute/vet.go looks at the argument's own type (*QDialog), not the parameter's, so a parent passed as a concrete wrapper is not seen as a parent. Only a parent held in an interface variable is recognised.
- Blind spots: the dialog in item 4 is not flagged (Exec and Show count as "released"), and neither is a parentless Go subclass.
- gui-goroutine ignores the root package, so go func() { qute.Click(w) }() passes.

9. A widget added to a layout that never gets a parent is leaked (confirmed, final pass)

    lay := qtwidgets.NewQVBoxLayout(nil)
    lay.AddWidget(qtwidgets.NewQLabelWithText("x", nil))   // drop both

- 20 of 20 labels were still alive after GC. AddWidget marks the label Parented at once, but Qt only reparents it when the layout is installed on a widget. The layout is collected, and the label is left with no owner on either side.
- It is a leak, not a crash. The fix is to apply the transfer only when the layout has a parent widget, or to let rule 7 work in reverse: a Parented QObject that has no Qt parent could go back to Owned.

10. A handler panic under qute.PostSync is caught after it has crossed Qt (confirmed, final pass)

- Outside qute.Run, a panic in a signal handler that runs inside a PostSync call unwinds through Qt's C++ frames, is recovered by PostSync on the GUI thread and re-raised in the calling goroutine.
- The stack shown is the caller's, so the handler's own stack is lost. If the caller recovers, the app carries on with Qt in whatever state the skipped C++ frames left it.
- CLAUDE.md says a handler panic under qute.Main "still crashes the program"; through PostSync it does not have to. PostSync could capture at the cgo boundary the way Run does.

11. Smaller things

- Naming: some generated names come straight from C++ parameter names: NewQVariantWithIArg, WithBArg, WithLl, WithUll, WithD, WithQchar, WithStringArg. NewQVariantOf covers the need, but the claim "every overload has a proper name" is generous.
- Stray file: qtgui/qtexttablecell_gen.go.broken (8.5K) is in the tree, hidden by a "*.broken" line in .gitignore. It looks like debris from an earlier session.
- CI: the generate job runs git diff --exit-code, which misses a new untracked generated file. CI does not run gofmt -l or qute vet.
- rt.post has a small race: a Post that reads appRunning as false just before AppStarted drains the pending list is appended afterwards and never runs. It needs a goroutine posting at the exact moment Main starts; I did not reproduce it.
- depends-on is only attached to plain and value classes (rt.Wrap). A notify-dtor or QObject class given depends-on would silently get nothing; the generator could warn.
- Licence: the repo is GPL-3.0, which is stricter than Qt's LGPL and makes every app built with qute GPL. If that is not the intent, LGPL or a permissive licence would match the "bindings" use. The README does not mention the licence.
- Off-thread calls are unchecked in release builds: b.Text() from a goroutine returned normally. This is documented (qute_debug adds the check); I note it only because the first goal says misuse is always a clear panic.

Checked and fine

- Delete() of a button or its window inside its own clicked handler does not crash in a release build.
- A Go model's Data() costs about 3.4 microseconds per call from C++; a full repaint of an 800x600 table took 10 ms. No problem there.
- The scaffold from "qute new" builds and its tests pass.
- Final pass: the ASan and cgocheck2 suites pass, and so does the race detector on the root package and internal/rt; examples/hello renders its screenshot; every qute.X and qtX.Y name cited in README.md and CLAUDE.md exists.
- Final pass: strings with an embedded NUL, empty strings, invalid UTF-8 and nil byte slices all round-trip sanely. Disconnect() inside the connection's own handler works. Value-class signal arguments are owned copies and are freed.
- I spot-checked about 40 well-known ownership rules (setModel, setItemDelegate, setMenu, addMenu, setStyle, setCompleter, setValidator, setScene, setDocument, takeAt, clone, setMimeData, setGraphicsEffect, setLayout and others) against Qt's documented behaviour and found none wrong.
- The runtime (internal/rt) reads cleanly: registry, serial numbers, keep sets and the cleanup queue hold together, and I found no new hole in them beyond the post race above.

Suggested order: 1 and 2 (safety), then 3 (largest user impact), then 7, 8 and 9 (cheap), then 5, 6, 10 and 4.
